# DEF-001 — concurrent requests corrupt the shared SQLite connection

| | |
|---|---|
| Found by | `verify:perf` — the k6 smoke, five users for thirty seconds. Scorecard: CS-008 *Requests failing under load* measured 5.00 against `< 1` — **MISSED** |
| Requirement | NFR-002 (nothing goes missing), FR-001, FR-008 |
| Classified | **Real defect.** Not flaky: it fails on every run with more than one user, and never with one |

## Evidence

```
http_req_failed................: 5.00% 4 out of 80
sqlite3.InterfaceError: bad parameter or other API misuse
  File "dues/sqlite_store.py", line 39, in has
ValueError: not enough values to unpack (expected 2, got 0)
```

Every failing request was a `POST /payments/upi` or `GET /reminders` that overlapped another request.

## Cause

The API opens **one** SQLite connection (`check_same_thread=False`) and the web server answers requests on
several threads. Two threads used the connection at once; SQLite's Python driver does not allow that.

## Why the earlier layers missed it

Unit tests, scenarios and the in-process API tests all make **one request at a time**. Nothing before the
performance smoke ever had two requests in flight. The Postman run passed too — it is sequential.

## The test that pins it

`code/tests/test_concurrency.py::test_def_001_concurrent_payments_and_reads_do_not_corrupt_the_connection` —
eight threads, four hundred payments and reads, on the store directly: the lowest layer that can see it.
Without the fix it fails on every run (`3 of 3`); with it, it passes.

## The fix

`Store` in `dues/api.py` holds a lock; every use of the connection goes through it. The smallest change that
removes the cause. A connection per request, or a server database, is for Session 17 (readiness) — logged in
`tech-debt.md`.
